## 项目一句话定义
这是一个基于 React + Node.js + MySQL 的 AI 视频复刻系统，核心目标是把“原始视频”转成“可分析、可拆解、可编辑、可重生成、可拼接下载”的完整生产链路。

## 核心业务主流程

### 1. 视频上传
- 用户在前端上传原始视频。
- 前端先做基础校验：格式、大小、时长上限、是否重复上传。
- 后端保存原视频文件并写入视频记录。
- 后端提取视频基础元数据，如时长、分辨率、编码格式。

### 2. 全片分析
- 后端调用 Gemini 对整条视频做第一次分析。
- 产出内容至少包含：
  - 完整剧情摘要
  - 角色列表与角色形象描述
  - 每个镜头或场景的背景描述
  - 切镜头时间锚点
- 分析结果持久化到数据库，前端展示分析结果。

### 3. 视频分割
- 后端根据时间锚点调用 FFmpeg 切分原视频。
- 每个片段生成独立文件，并在数据库中创建片段记录。
- 分割任务应设计为异步任务，便于进度跟踪与失败重试。

### 4. 片段级分析
- 后端对每个视频片段再次调用 Gemini。
- 产出片段级结构化信息：
  - 主要人物
  - 场景
  - 动作
  - 片段剧情描述
  - 可编辑的初始提示词
- 前端以卡片列表形式展示每个片段。

### 5. 提示词优化与角色映射
- 用户可以在前端编辑片段提示词。
- 点击“优化提示词”后，后端调用 Gemini 优化文案。
- 优化后的提示词中，角色名称以 `@角色名` 形式高亮展示。
- 实际提交给生成模型时，不直接传 `@角色名`，而是先解析为该角色对应的完整角色形象提示词。
- 这一步的关键不是单纯染色，而是建立“角色标签 -> 角色设定 Prompt”的稳定映射机制。

### 6. 片段重生成
- 前端基于片段原始内容、整体剧情、角色映射结果和用户编辑提示词，发起生成请求。
- 后端调用 Seed Dance API 生成对应的新片段。
- 生成结果需要回写到片段或任务记录中，并支持失败重试、状态追踪和结果预览。

### 7. 视频拼接与下载
- 用户确认所需片段后，发起视频拼接。
- 后端按照片段顺序调用 FFmpeg 合并视频。
- 前端展示实时进度。
- 合并完成后提供下载入口。

## 推荐的系统模块拆分

### 前端职责
- 上传视频与展示上传进度
- 展示整片分析结果
- 展示片段卡片与片段状态
- 编辑/优化提示词
- 触发片段生成与展示生成结果
- 展示拼接进度并下载最终视频

### 后端职责
- 文件上传、文件管理、静态资源访问控制
- MySQL 数据持久化
- Gemini 接入与结果结构化
- FFmpeg 分割与拼接
- Seed Dance 生成任务调度
- 异步任务状态管理
- WebSocket 或 SSE 进度推送

### 数据库职责
- 存储项目、视频、整片分析、片段、生成任务等核心数据
- 保证任务状态一致性
- 支持进度查询、结果回显和后续审计

## 建议统一的数据流设计

### 上传阶段
`前端上传文件 -> 后端落盘 -> 提取元数据 -> videos 表写入 -> 返回 videoId`

### 全片分析阶段
`前端发起分析 -> 后端创建分析任务 -> Gemini 分析 -> analyses 表落库 -> 前端拉取或订阅结果`

### 分割阶段
`前端确认时间锚点 -> 后端创建分割任务 -> FFmpeg 分割 -> segments 表批量写入 -> 前端刷新片段列表`

### 生成阶段
`前端提交片段提示词 -> 后端解析 @角色标签 -> 拼装最终模型提示词 -> Seed Dance 生成 -> 回写结果地址`

### 拼接阶段
`前端发起拼接 -> 后端创建拼接任务 -> FFmpeg 合并 -> 输出最终文件 -> 返回下载地址`

## 后续实现时建议优先坚持的工程决策

### 1. 前后端技术栈
- 前端：React + Vite + Tailwind CSS + Zustand
- 后端：Node.js + Express + Sequelize
- 数据库：MySQL 8
- 异步任务：优先使用队列化方案，推荐 BullMQ + Redis；如果阶段 1 先不引入 Redis，则先抽象任务接口，避免后续重构成本过高
- 实时进度：推荐 Socket.IO，若实现成本需要控制，可先用轮询，后续再切 WebSocket

### 2. 文件存储策略
- 原视频、分割片段、生成片段、拼接结果都存文件系统或对象存储，不直接存数据库二进制
- 数据库只存路径、URL、状态、元数据
- 上传目录按业务分类，例如 `videos/`、`segments/source/`、`segments/generated/`、`outputs/`

### 3. AI 结果结构化
- Gemini 返回值必须经过后端二次结构化和校验，不能直接信任模型原始文本
- 时间锚点必须转成统一格式，例如：
```json
[
  {
    "startTime": 0.0,
    "endTime": 3.2,
    "sceneSummary": "主角走进咖啡馆"
  }
]
```
- 角色信息必须具备稳定 ID，避免后续只靠中文名称匹配

### 4. 任务状态模型
- 上传、分析、分割、生成、拼接都应有明确状态
- 推荐统一状态枚举：`pending`、`processing`、`completed`、`failed`
- 所有长任务都要保留错误信息和更新时间，便于重试和排障

## 每次改代码前必须遵守的开发约束

### 架构约束
- 所有功能实现都必须遵循“前端展示层 / 后端接口层 / 服务层 / 数据层”分层思路。
- 不允许把 Gemini、FFmpeg、Seed Dance 的调用逻辑直接写进路由层。
- 不允许前端组件直接拼接复杂业务规则，业务逻辑要进入 hooks、store 或 service。

### 数据约束
- 所有数据库字段命名、状态枚举、时间格式必须统一。
- 关键 JSON 字段必须定义稳定结构，不能一阶段一个格式。
- 不把模型原始响应直接作为前端最终展示对象，必须做清洗和转换。

### 接口约束
- RESTful API 路径、方法、状态码、错误格式保持一致。
- 长耗时操作必须异步化，并能查询进度。
- 文件上传、视频分析、分割、生成、拼接接口都要支持失败后的可恢复设计。

### 安全约束
- 所有外部输入必须校验。
- 所有路径、密钥、数据库配置必须来自环境变量。
- 上传文件必须校验 MIME、扩展名、大小和目标目录。
- 不在日志中输出 API Key、数据库密码、完整用户敏感数据。

### 性能约束
- 视频处理和 AI 调用默认按异步任务设计，不阻塞主请求。
- 大文件处理优先使用流式或磁盘中转，不做大对象常驻内存。
- 数据查询默认考虑索引和分页，不直接全量扫描。

### 可维护性约束
- 所有新增功能必须同时补齐最小可用文档或注释。
- 公共常量、错误码、状态枚举统一管理。
- 复杂功能先抽象接口，再接入第三方能力，避免后续替换 API 时牵一发而动全身。

### 测试约束
- 至少覆盖主干 Happy Path 和核心失败场景。
- 外部 AI 服务、FFmpeg 和对象存储接口要可 Mock。
- 每个阶段结束时都要能说明“已验证什么、未验证什么”。

## Git 工作流基线
- 稳定分支：`main`
- 开发集成分支：`develop`
- 功能分支：`feature/<stage-or-feature-name>`
- 修复分支：`bugfix/<issue-name>`
- 紧急修复分支：`hotfix/<issue-name>`

### 推荐流程
1. 先初始化 Git 仓库并创建 `main`
2. 从 `main` 创建 `develop`
3. 每个阶段从 `develop` 拉出功能分支
4. 功能完成后合并回 `develop`
5. 你确认阶段验收通过后，再把 `develop` 合并到 `main`
